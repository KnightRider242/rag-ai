# Developer guide: learn the current RAG-AI pipeline

RAG-AI currently accepts PDF, plain-text, and Markdown uploads for development-only parsing and chunking. With a second explicit development flag, it can embed chunks through **local Ollama** and store the original document, chunks, and vectors in PostgreSQL/pgvector. It does not retrieve evidence or generate answers yet. Follow the [README](../README.md) for setup and the [codebase map](CODEBASE_MAP.md) for a compact module index.

## Follow one document through the code

1. **FastAPI decides what exists.** `src/rag_ai/main.py` builds the app from Pydantic `Settings`. `/health` is always present. Document routes appear only with development opt-in, and indexing needs its own flag. The flag is a development guard, not user authentication. `src/rag_ai/api/documents.py` connects HTTP uploads to the processing functions.
2. **Parsing turns bytes into a typed document.** `documents/parser.py` validates the filename extension and MIME declaration, upload size, PDF structure or UTF-8 text, and extraction limits. PyMuPDF reads PDFs page by page; scanned PDFs without extractable text are rejected rather than OCR'd. The `ParsedDocument` model carries text and source metadata. Its document ID is a SHA-256 hash of the original bytes, not an authorization token.
3. **Chunking creates smaller units for later retrieval.** `documents/chunker.py` uses LangChain's standalone `langchain-text-splitters` package and `RecursiveCharacterTextSplitter` with server-configured size and overlap. It splits each PDF page separately, preserving page numbers, and splits TXT/Markdown as one text source. The output includes ordered chunks, source metadata, and deterministic IDs. Boundary choices can make actual overlap vary.
4. **Indexing coordinates local inference.** `documents/indexer.py` takes a `ParsedDocument` and its chunks, checks chunk limits, and calls the small `EmbeddingProvider` interface in `embeddings/base.py`. Its Ollama implementation in `embeddings/ollama.py` sends batches of at most 16 texts to the configured loopback endpoint. Ollama returns numerical vectors; the code measures their dimensions rather than assuming every model produces 768 values. The initial `embeddinggemma:300m` integration was previously measured at 768. The provider also checks the model digest to detect a changed model under the same name.
5. **PostgreSQL stores the evidence for later work.** `storage/postgres.py` stages batches in a temporary table, then commits the document, chunks, and pgvector embeddings in one final transaction. The schema in `storage/migrations/0001_initial.sql` uses collection-scoped keys and records model identity and dimensions. A failed final write leaves the previous permanent index intact. Original bytes remain until explicit storage-layer deletion; automatic expiry and an HTTP deletion route do not exist. Migrations are explicit, not an app-startup side effect.

An embedding is a numeric representation of text. pgvector stores these arrays, but storage alone is not semantic retrieval: Phase 5 must add authorized similarity queries, compatible-model filtering, and evaluation. LangChain currently supplies **text splitting only**; LCEL, broader LangChain chains, LangGraph agent workflows, and MCP tool integration are not present. LangGraph and MCP are planned for later phases after retrieval and answer generation have clear contracts. See [roadmap](ROADMAP.md) and [architecture decisions](ARCHITECTURE_DECISIONS.md).

## Navigate, test, and debug

Start from the behavior you are studying: route in `api/`, model and logic in `documents/` or `embeddings/`, persistence in `storage/`, and matching `tests/test_*.py`. Use targeted symbol searches such as `rg -n 'def chunk_document|class ChunkedDocument' src tests` and read the caller plus its immediate dependency. When a failure crosses boundaries, check the route's settings, parser error, chunk budget, provider model/dimension validation, then migration status and storage transaction. Avoid printing document content or credentials while debugging.

Run `python -m pytest -q` for the default suite. It exercises the API, parser, chunker, and mocked provider behavior; live PostgreSQL/Ollama tests are opt-in and use disposable schemas. See the [README test section](../README.md#tests) for their prerequisites. If an upload is rejected, compare the relevant test in `tests/test_documents.py` or `tests/test_chunking.py`; for a model or storage error, start with `tests/test_embeddings.py` and the opt-in persistence tests. Never point destructive integration tests at a database with real documents.

The architecture favors a small provider interface, collection-scoped keys, explicit migrations, and local-only inference so each boundary can be reasoned about separately. These choices do not provide production access control. The development routes lack authentication and collection authorization, and public exposure is prohibited. See the [security test plan](SECURITY_TEST_PLAN.md) for current limits and future requirements.

## Study each new feature

Before implementation, describe the user behavior, learning goal, alternatives, and trust boundaries. After implementation, trace one input through the changed modules, read the relevant tests, run the smallest meaningful check, and explain a failure path and a design trade-off in your own words. Record significant decisions in [architecture decisions](ARCHITECTURE_DECISIONS.md), keeping planned behavior separate from code that exists.
