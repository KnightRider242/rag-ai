# Developer guide: learn the current RAG-AI pipeline

RAG-AI accepts PDF, plain-text, and Markdown uploads for development-only parsing and chunking. Separate development flags enable local Ollama indexing in PostgreSQL/pgvector, semantic search, and single-turn cited answers. Follow the [README](../README.md) for setup and the [codebase map](CODEBASE_MAP.md) for a compact module index.

## Follow one document through the code

1. **FastAPI decides what exists.** `src/rag_ai/main.py` builds the app from Pydantic `Settings`. `/health` is always present. Document routes appear only with development opt-in, and indexing needs its own flag. The flag is a development guard, not user authentication. `src/rag_ai/api/documents.py` connects HTTP uploads to the processing functions.
2. **Parsing turns bytes into a typed document.** `documents/parser.py` validates the filename extension and MIME declaration, upload size, PDF structure or UTF-8 text, and extraction limits. PyMuPDF reads PDFs page by page; scanned PDFs without extractable text are rejected rather than OCR'd. The `ParsedDocument` model carries text and source metadata. Its document ID is a SHA-256 hash of the original bytes, not an authorization token.
3. **Chunking creates smaller units for later retrieval.** `documents/chunker.py` uses LangChain's standalone `langchain-text-splitters` package and `RecursiveCharacterTextSplitter` with server-configured size and overlap. It splits each PDF page separately, preserving page numbers, and splits TXT/Markdown as one text source. The output includes ordered chunks, source metadata, and deterministic IDs. Boundary choices can make actual overlap vary.
4. **Indexing coordinates local inference.** `documents/indexer.py` takes a `ParsedDocument` and its chunks, checks chunk limits, and calls the small `EmbeddingProvider` interface in `embeddings/base.py`. Its Ollama implementation in `embeddings/ollama.py` sends batches of at most 16 texts to the configured loopback endpoint. Ollama returns numerical vectors; the code measures their dimensions rather than assuming every model produces 768 values. The initial `embeddinggemma:300m` integration was previously measured at 768. The provider also checks the model digest to detect a changed model under the same name.
5. **PostgreSQL stores the evidence for later work.** `storage/postgres.py` stages batches in a temporary table, then commits the document, chunks, and pgvector embeddings in one final transaction. The schema in `storage/migrations/0001_initial.sql` uses collection-scoped keys and records model identity and dimensions. A failed final write leaves the previous permanent index intact. Original bytes remain until explicit storage-layer deletion; automatic expiry and an HTTP deletion route do not exist. Migrations are explicit, not an app-startup side effect.

An embedding is a numeric representation of text. A query follows the same local Ollama embedding boundary as indexed chunks; `retrieval/service.py` checks for one finite, nonzero vector and passes its model name, digest, and measured dimensions to `storage/postgres.py`. The store checks compatibility against **actual indexed embeddings** in one read-only snapshot. It then filters candidates by collection, model, revision, dimensions, and nonzero norm before pgvector's cosine-distance operator (`<=>`) ranks them. Smaller distance means closer direction. Exact search has stable ID tie-breaking and returns source metadata without raw vectors.

`api/retrieval.py` exposes this path only with a separate development flag and runs the synchronous provider/database work in a threadpool. A missing collection yields no results; a model, digest, or dimension mismatch yields an explicit 409 response. `retrieval/langchain.py` wraps the same service in LangChain Core's `BaseRetriever`; `invoke(query)` returns `Document` objects with chunk text as `page_content` and source/distance fields as metadata. LangChain supplies **text splitting and this thin retriever interface**. Phase 6 answer generation uses a separate small RAG service, not an LCEL chain. LangGraph agent workflows and MCP tools are not present. See [roadmap](ROADMAP.md) and [architecture decisions](ARCHITECTURE_DECISIONS.md).

For an already constructed local `RetrievalService`, adapter usage is:

```python
retriever = RAGAIBaseRetriever(service=service, collection_id=collection_id, top_k=5)
documents = retriever.invoke("How does battery cooling work?")
```

The caller owns the provider lifetime and must close it after use. The adapter does not select a provider or bypass the store's collection filter.

`retrieval/evaluation.py` scores actual ranked chunk IDs against expected IDs: Recall@K is the fraction of expected IDs retrieved, Hit@K records any hit, and MRR averages the reciprocal rank of the first hit **within the requested top K** (zero when no hit appears). Synthetic cases live separately in `tests/evaluation/semantic_cases.json`: nine one-chunk documents include topic neighbors and misleading shared words, while four paraphrased questions each identify one relevant source. The test obtains expected chunk IDs from those indexed sources before searching. SQL/ranking tests use controlled vectors; the opt-in semantic check measures K=1 and K=3 using local Ollama. The 2026-10-29 run ranked all four sources first (Recall@1, Recall@3, Hit@1, Hit@3, and MRR@3 all 1.0). This is a small regression check, not a production retrieval benchmark or a guarantee for other queries or model revisions.

## Study the Phase 6 answer path

Start at `api/answers.py`: the answer route validates JSON and calls `RAGService.answer()` in a threadpool. `rag/service.py` delegates search to the existing `RetrievalService`; retrieval ends when ranked chunks arrive. `rag/context.py` assigns S1/S2 labels and bounds text without silent truncation. `rag/prompts.py` places it inside a delimited, untrusted evidence section. The `GenerationProvider` contract in `generation/base.py` accepts the default local Ollama `/api/chat`, explicitly selected OpenAI Responses, or explicitly selected Gemini `generateContent` implementation. Each validates structured output before the unchanged `RAGService` maps cited labels back to retrieved chunk metadata. A missing result or model abstention returns `insufficient_evidence`; an invented label fails closed. Valid labels prove provenance, not factual support.

For Phase 7B, `core/config.py` reads `GENERATION_PROVIDER`, the cloud enable flag, a JSON UUID allowlist, supported model, and a secret API key. `api/answers.py` checks the collection allowance before any retrieval or OpenAI provider construction. `generation/openai.py` uses fixed HTTPS, `store: false`, no tools, and a root-object strict schema. It accepts one completed assistant text output, then converts it to the same `GeneratedAnswer` model. It maps `num_predict` to `max_output_tokens` and uses `reasoning.effort=none`; Ollama's context and temperature settings are not sent. This keeps citation checks in one place while making cloud transfer an explicit operator decision. A key by itself grants no transfer permission, and this allowlist does not identify a caller.

Phase 7C reuses that cloud gate for `GENERATION_PROVIDER=gemini`. `generation/gemini.py` calls Google's fixed `generateContent` host with `systemInstruction`, one user `contents` item, and `generationConfig.responseFormat.text` for JSON. It requests one candidate and maps `num_predict` to `maxOutputTokens`; it leaves thinking and temperature at model defaults. The provider accepts only a successful `STOP` candidate with one model-role text part and a compatible version identifier, then validates the same `GeneratedAnswer` domain model. Safety blocks, tool parts, bad JSON, and unsupported versions fail as generation errors. This branch depends on unmerged OpenAI work; only mocked Gemini HTTP behavior has been tested. No Gemini cloud call is authorized.

For debugging, distinguish retrieval 409 compatibility failures and 503 database failures from generation 502 failures. A cloud 403 means the operator gate or collection allowlist denied transfer. Check the selected provider, model allowlist, credential presence, and sanitized HTTP category; then inspect response completion, model version, and domain validation with synthetic local mocks. Do not print prompts, document text, provider response bodies, or credentials. `tests/test_rag_service.py` exercises citations and abstention; `tests/test_generation.py`, `tests/test_openai_generation.py`, and `tests/test_gemini_generation.py` cover response errors; `tests/test_answer_api.py` covers route and cloud gates; the opt-in `tests/test_rag_integration.py` checks local end-to-end answers. A prior live OpenAI request received HTTP 429; Gemini HTTP tests are mocked, so neither has a verified live quality result.

## Navigate, test, and debug

Start from the behavior you are studying: route in `api/`, model and logic in `documents/`, `embeddings/`, or `retrieval/`, persistence in `storage/`, and matching `tests/test_*.py`. Use targeted symbol searches such as `rg -n 'def retrieve|def search|class RAGAIBaseRetriever' src tests` and read the caller plus its immediate dependency. When search fails, check the route flag and bind address, local Ollama availability/model digest, migration status, then the collection's **indexed** model metadata and dimensions. A 409 means compatibility failed; 502 points to query embedding; 503 points to database configuration or availability. Do not print query text, document content, vectors, or credentials while debugging.

Run `python -m pytest -q` for the default suite. It exercises the API, parser, chunker, mocked provider, search service/adapter, and metric behavior; live PostgreSQL/Ollama tests are opt-in and use disposable schemas. See the [README test section](../README.md#tests) for their prerequisites. If an upload is rejected, compare `tests/test_documents.py` or `tests/test_chunking.py`; for search failures, start with `tests/test_retrieval.py`, then the opt-in `tests/test_retrieval_integration.py`. Never point destructive integration tests at a database with real documents.

The architecture favors a small provider interface, collection-scoped keys, explicit migrations, and local-only inference so each boundary can be reasoned about separately. These choices do not provide production access control. The development routes lack authentication and collection authorization, and public exposure is prohibited. See the [security test plan](SECURITY_TEST_PLAN.md) for current limits and future requirements.

## Study each new feature

Before implementation, describe the user behavior, learning goal, alternatives, and trust boundaries. After implementation, trace one input through the changed modules, read the relevant tests, run the smallest meaningful check, and explain a failure path and a design trade-off in your own words. Record significant decisions in [architecture decisions](ARCHITECTURE_DECISIONS.md), keeping planned behavior separate from code that exists.
