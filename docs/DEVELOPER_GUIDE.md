# Developer guide: learn the current RAG-AI pipeline

RAG-AI accepts PDF, plain-text, and Markdown uploads for development-only parsing and chunking. Separate development flags enable local Ollama indexing in PostgreSQL/pgvector, semantic search, and single-turn cited answers. Basic PDF raster inspection is merged on `main`; this branch adds vector/table inspection, preview, and local vision analysis. Follow the [README](../README.md) for setup and the [codebase map](CODEBASE_MAP.md) for a module index.

## Follow one document through the code

1. **FastAPI decides what exists.** `src/rag_ai/main.py` builds the app from Pydantic `Settings`. `/health` is always present. Document routes appear only with development opt-in, and indexing needs its own flag. The flag is a development guard, not user authentication. `src/rag_ai/api/documents.py` connects HTTP uploads to the processing functions.
2. **Parsing turns bytes into a typed document.** `documents/parser.py` validates the filename extension and MIME declaration, upload size, PDF structure or UTF-8 text, and extraction limits. PyMuPDF reads PDFs page by page; scanned PDFs without extractable text are rejected rather than OCR'd. The `ParsedDocument` model carries text and source metadata. Its document ID is a SHA-256 hash of the original bytes, not an authorization token.
3. **Chunking creates smaller units for later retrieval.** `documents/chunker.py` uses LangChain's standalone `langchain-text-splitters` package and `RecursiveCharacterTextSplitter` with server-configured size and overlap. It splits each PDF page separately, preserving page numbers, and splits TXT/Markdown as one text source. The output includes ordered chunks, source metadata, and deterministic IDs. Boundary choices can make actual overlap vary.
4. **Indexing coordinates local inference.** `documents/indexer.py` takes a `ParsedDocument` and its chunks, checks chunk limits, and calls the small `EmbeddingProvider` interface in `embeddings/base.py`. Its Ollama implementation in `embeddings/ollama.py` sends batches of at most 16 texts to the configured loopback endpoint. Ollama returns numerical vectors; the code measures their dimensions rather than assuming every model produces 768 values. The initial `embeddinggemma:300m` integration was previously measured at 768. The provider also checks the model digest to detect a changed model under the same name.
5. **PostgreSQL stores the evidence for later work.** `storage/postgres.py` stages batches in a temporary table, then commits the document, chunks, and pgvector embeddings in one final transaction. The schema in `storage/migrations/0001_initial.sql` uses collection-scoped keys and records model identity and dimensions. A failed final write leaves the previous permanent index intact. Original bytes remain until explicit storage-layer deletion; automatic expiry and an HTTP deletion route do not exist. Migrations are explicit, not an app-startup side effect.

An embedding is a numeric representation of text. A query follows the same local Ollama embedding boundary as indexed chunks; `retrieval/service.py` checks for one finite, nonzero vector and passes its model name, digest, and measured dimensions to `storage/postgres.py`. The store checks compatibility against **actual indexed embeddings** in one read-only snapshot. It then filters candidates by collection, model, revision, dimensions, and nonzero norm before pgvector's cosine-distance operator (`<=>`) ranks them. Smaller distance means closer direction. Exact search has stable ID tie-breaking and returns source metadata without raw vectors.

`api/retrieval.py` exposes this path only with a separate development flag and runs the synchronous provider/database work in a threadpool. A missing collection yields no results; a model, digest, or dimension mismatch yields an explicit 409 response. `retrieval/langchain.py` wraps the same service in LangChain Core's `BaseRetriever`; `invoke(query)` returns `Document` objects with chunk text as `page_content` and source/distance fields as metadata. LangChain supplies **text splitting and this thin retriever interface**. Phase 6 answer generation uses a separate small RAG service, not an LCEL chain. LangGraph agent workflows and MCP tools are not present. See [roadmap](ROADMAP.md) and [architecture decisions](ARCHITECTURE_DECISIONS.md).

For an already constructed local `RetrievalService`, adapter usage is:

```python
retriever = RAGAIBaseRetriever(service=service, collection_id=collection_id, top_k=5)
documents = retriever.invoke("How does battery cooling work?")
```

The caller owns the provider lifetime and must close it after use. The adapter does not select a provider or bypass the store's collection filter.

`retrieval/evaluation.py` scores actual ranked chunk IDs against expected IDs: Recall@K is the fraction of expected IDs retrieved, Hit@K records any hit, and MRR averages the reciprocal rank of the first hit **within the requested top K** (zero when no hit appears). Synthetic cases live separately in `tests/evaluation/semantic_cases.json`: nine one-chunk documents include topic neighbors and misleading shared words, while four paraphrased questions each identify one relevant source. The test obtains expected chunk IDs from those indexed sources before searching. SQL/ranking tests use controlled vectors; the opt-in semantic check measures K=1 and K=3 using local Ollama. The 2026-10-29 run ranked all four sources first (Recall@1, Recall@3, Hit@1, Hit@3, and MRR@3 all 1.0). This is a small regression check, not a production retrieval benchmark or a guarantee for other queries or model revisions.

## Study the Phase 6 answer path

Start at `api/answers.py`: the answer route validates JSON and calls `RAGService.answer()` in a threadpool. `rag/service.py` delegates search to the existing `RetrievalService`; retrieval ends when ranked chunks arrive. `rag/context.py` assigns S1/S2 labels and bounds text without silent truncation. `rag/prompts.py` places it inside a delimited, untrusted evidence section. The separate `GenerationProvider` in `generation/base.py` sends a local Ollama `/api/chat` request through `generation/ollama.py`, with JSON-schema output and resource settings. The provider validates JSON before `RAGService` maps each cited label back to retrieved chunk metadata. A missing result or model abstention returns `insufficient_evidence`; an invented label fails closed. Valid labels prove provenance, not factual support.

For debugging, distinguish retrieval 409 compatibility failures and 503 database failures from generation 502 failures. Check local model availability, then whether the retrieved chunks actually support the question; do not print prompts, document text, or credentials. `tests/test_rag_service.py` exercises citations and abstention; `tests/test_generation.py` covers Ollama response errors; `tests/test_answer_api.py` covers route gating; the opt-in `tests/test_rag_integration.py` indexes synthetic sources and checks end-to-end answers. This is a small rule-based grounding check, not a general factuality guarantee.

## Navigate, test, and debug

Start from the behavior you are studying: route in `api/`, model and logic in `documents/`, `embeddings/`, or `retrieval/`, persistence in `storage/`, and matching `tests/test_*.py`. Use targeted symbol searches such as `rg -n 'def retrieve|def search|class RAGAIBaseRetriever' src tests` and read the caller plus its immediate dependency. When search fails, check the route flag and bind address, local Ollama availability/model digest, migration status, then the collection's **indexed** model metadata and dimensions. A 409 means compatibility failed; 502 points to query embedding; 503 points to database configuration or availability. Do not print query text, document content, vectors, or credentials while debugging.

Run `python -m pytest -q` for the default suite. It exercises the API, parser, chunker, mocked provider, search service/adapter, and metric behavior; live PostgreSQL/Ollama tests are opt-in and use disposable schemas. See the [README test section](../README.md#tests) for their prerequisites. If an upload is rejected, compare `tests/test_documents.py` or `tests/test_chunking.py`; for search failures, start with `tests/test_retrieval.py`, then the opt-in `tests/test_retrieval_integration.py`. Never point destructive integration tests at a database with real documents.

The merged [local PDF-to-answer verification](LOCAL_RAG_TESTING.md) calls the real FastAPI routes through `tests/test_local_rag_e2e.py`. It checks page-aware parsing/chunking, indexing, search, answers, abstention, and collection filtering in a disposable test schema. Run `python -m pytest -q -s tests/test_local_rag_e2e.py` with the dedicated test database and local Ollama opt-in settings described there. Debug in route order: HTTP status, Ollama availability/model digest, retrieved page and ranking, then claim text against its cited evidence. An early live attempt cited the correct page but named the emergency-stop button instead of the relay; the synthetic source was clarified and the relay assertion retained. Citation validity proves a retrieved source reference, not factual grounding. The guide separates this automated result from the user's manual Swagger observations.

The architecture favors a small provider interface, collection-scoped keys, explicit migrations, and local-only inference so each boundary can be reasoned about separately. These choices do not provide production access control. The development routes lack authentication and collection authorization, and public exposure is prohibited. See the [security test plan](SECURITY_TEST_PLAN.md) for current limits and future requirements.

## Phase 8 visual processing on main

Start with `api/visual.py` and `documents/visual.py`: inspection distinguishes embedded raster occurrences, vector paths, and PyMuPDF-detected tables. These are metadata or extracted cells, not visual interpretation. `documents/render.py` turns one displayed PDF page/region into a bounded PNG. `api/vision.py` delegates that PNG, or a verified standalone PNG/JPEG, to `vision/ollama.py`; `vision/evidence.py` attaches the upload hash, filename, page, and region after the model responds. The model supplies only description, observations, and limitations. PDF coordinates are displayed-page points; image coordinates are native pixels. See [local visual testing](LOCAL_RAG_TESTING.md#phase-8-visual-testing-on-main) for Swagger and synthetic checks.

When debugging, check route flags and PDF/image validation first (HTTP 4xx), then page/region limits, then local Ollama model availability and response validity (502). Internal logs record a fixed category for HTTP status, transport, timeout, or response-validation failures; public errors remain generic. A table missed by `find_tables()` is a detection limit; an invented object in a description is a model-grounding failure. Neither becomes a text-RAG citation. Run `python -m pytest -q tests/test_visual_inspection.py tests/test_visual_structure.py tests/test_vision_provider.py tests/test_multimodal_api.py` for synthetic and mocked checks. A later 15-request local check with `qwen3-vl:4b-instruct` returned HTTP 200 throughout but misread a small label and overcounted fields, so live success does not prove visual accuracy.

## Phase 9A.1 visual metadata persistence

`documents/visual_elements.py` adapts bounded Phase 8 inspection into raster, heuristic-table, and visible vector-path occurrences. It rounds coordinates to four decimal places before hashing and storing them. Repeated same-box occurrences have separate ordinal IDs; paths are source geometry, not semantic diagrams. `storage/visual.py` verifies original PDF SHA-256, extracts outside a write transaction, then locks the document row, rechecks identity, and replaces one extractor's complete set atomically. `api/visual_elements.py` offers separately gated POST indexing and paginated GET listing. A text reindex of the same source preserves visual records; document deletion cascades them. Check schema version 4 on this branch before diagnosing a 503, and use only a verified disposable database for integration tests.

## Phase 9A.2 persistent local interpretations

`api/interpretations.py` adds separately gated analyze, list, and retrieve routes under a complete collection/document/element key. `vision/persistence.py` loads a stored element and the original indexed PDF, verifies SHA-256 and displayed-page geometry, renders one bounded region with the Phase 8 renderer, hashes the PNG, and calls the existing local vision provider with a predefined task and `stored_visual_v1` prompt version. `vision/ollama.py` checks Ollama's `/api/tags` digest before and after chat; the chat envelope must name the configured model. Ollama does not bind a chat response atomically to a digest, so a revision swapped between checks remains a provenance limit. No model is downloaded automatically.

`storage/interpretations.py` rechecks the PDF and exact element under database row locks after inference, then inserts one immutable row. A caller-supplied UUID request key returns the existing interpretation on retry; a different key creates a new history entry. A missing or changed element rejects the write. The database transaction covers only this final recheck and insert. Deleting the source element or document cascades interpretations. Stored descriptions are model-generated and explicitly unverified. The text-RAG answer endpoint does not consume them. To debug, inspect the route flag and schema version, source identity/geometry, Ollama tag identity and generation status, then the stored request key. Keep source and generated text out of logs.

## Phase 9B.1 local visual semantic retrieval

Enable `ENABLE_VISUAL_RETRIEVAL_ENDPOINT` only in development after an explicitly authorized schema-version-4 upgrade. POST `/collections/{collection_id}/visual-interpretations/index` with a document SHA-256, element SHA-256, and interpretation UUID to embed one existing interpretation. The service builds deterministic UTF-8 text from the unverified description and observations, calls the existing local embedding provider once, then locks and rechecks source rows before inserting the vector. Repeating the same request leaves the existing vector intact. POST `/collections/{collection_id}/visual-search` with `query` and `top_k` to rank compatible visual vectors and return source coordinates and unverified interpretation metadata. The provider embeds the query once. Debug model/revision/dimension conflicts through `embedding_spaces` and the stored vector metadata; inspect source deletion or replacement if a write returns 409. No Qwen3-VL call occurs during this phase. Combined text/visual ranking, answer citations, and image-pixel search are separate future work.

Before implementation, describe the user behavior, learning goal, alternatives, and trust boundaries. After implementation, trace one input through the changed modules, read the relevant tests, run the smallest meaningful check, and explain a failure path and a design trade-off in your own words. Record significant decisions in [architecture decisions](ARCHITECTURE_DECISIONS.md), keeping planned behavior separate from code that exists.
